# 发布签名配置

> 内部运维文档，不面向终端用户。

## 为什么需要它

agent 自升级是以 **root 替换二进制并重启**，且刻意不检查 `--allow-exec`——
理由是「从固定地址装带校验和的官方二进制」。但下载源可以由 `MOSS_RELEASE_BASE`
整体覆盖成镜像（境内机器直连 GitHub 会超时，这个入口是必需的），
而 `SHA256SUMS` 与二进制来自**同一个地址**。

于是校验和只能证明「传输没坏」，证不了「二进制是官方的」——能替换二进制的镜像
同样能替换清单。强制 https 挡住了被动中间人，挡不住一个敌意的镜像站。

签名把信任从**传输层**挪到**发布者**：清单由私钥签，agent 用编译进去的公钥验。
镜像站换掉任何一个字节，签名都对不上。

## 一次性配置（三步）

### 1. 生成密钥对

```bash
go run ./tools/sign -genkey
```

输出两个 base64 值。**私钥只会出现这一次**，不要存进仓库、不要发聊天工具。

### 2. 配到 GitHub

| 位置 | 名称 | 值 |
|---|---|---|
| Settings → Secrets and variables → Actions → **Secrets** | `MOSS_RELEASE_PRIVKEY` | 私钥 |
| Settings → Secrets and variables → Actions → **Variables** | `MOSS_RELEASE_PUBKEY` | 公钥 |

私钥进 Secrets（加密、日志里自动打码），公钥进 Variables（它本来就要编进
每个 agent 二进制，不是秘密）。

### 3. 发一版

下一次 `git tag v* && git push --tags` 时：

- release 产物里会多一个 `SHA256SUMS.sig`
- agent 二进制里会编入公钥，从此**强制**校验签名

## 顺序很重要

两个值必须**同时**配好。只配其一会出问题：

| 情况 | 后果 |
|---|---|
| 只配公钥（Variables） | agent 编入了公钥并强制校验，但 release 没有 `.sig` → **所有 agent 拒绝升级** |
| 只配私钥（Secrets） | release 带了签名，但 agent 没有公钥可验 → 退回校验和校验，签名白签 |
| 都不配 | 现状：https + 校验和，功能正常 |

第一种是唯一会造成实际影响的：机器不会坏，只是一键升级全部失败，
需要手动跑安装脚本，或者把 Variables 里的公钥删掉再发一版。

## 密钥轮换

私钥泄漏或需要定期轮换时：

1. `go run ./tools/sign -genkey` 生成新的一对
2. 先更新 **Secrets 里的私钥**，发一版 —— 这一版的 `.sig` 用新私钥签，
   但在役 agent 内置的还是旧公钥，**会拒绝升级**
3. 所以正确顺序是反过来的：**先不要动 Variables**，用旧密钥再发一版让机器都升上来；
   确认全部在役 agent 都是最新版之后，再同时换掉 Secrets 与 Variables 并发新版

换句话说：轮换必然伴随一次「所有机器手动升级」，除非同时支持新旧两把公钥。
当前实现只支持一把——这是刻意的取舍，多公钥会让「哪把钥匙还有效」变成需要
额外追踪的状态，而轮换是低频事件。真要轮换时，手动升一轮的成本可以接受。

## 校验行为

`agent/upgrade.go` 的 `verifySumsSignature`：

- 公钥为空 → 记一条日志，退回「https + 校验和」
- 公钥非法（长度不对、不是 base64）→ **拒绝安装**，不降级。构建坏掉不该静默变成校验被关掉
- 取不到 `.sig` → **拒绝安装**。否则敌意镜像只要不提供签名文件就能把校验降级掉
- 签名不匹配 → 拒绝安装

没有任何运行时开关能关掉签名校验。这类开关会被人为了「先升上去」打开，然后永远忘掉。
